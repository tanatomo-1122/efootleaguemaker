# efootleaguemaker

eFootball のリーグ戦を「作って・遊んで・データを残す」ためのウェブアプリです。
みんなが楽しめるリーグシステムを提供しながら、スカッド情報と試合結果を紐づけて蓄積し、
勝敗を左右する要因を分析できるようにすることを狙いとしています。

**構成**: Next.js (App Router) / Supabase PostgreSQL / Supabase Storage / OpenAI GPT-4o mini
デプロイ先は Vercel を想定しています。

---

## セットアップ

### 1. Supabase プロジェクトを作る

1. <https://supabase.com> でプロジェクトを作成（リージョンは東京 `ap-northeast-1` が無難）
2. 作成時のデータベースパスワードは後で使うので控えておく

### 2. テーブルを作る

Supabase ダッシュボード左の **SQL Editor** を開き、`supabase/schema.sql` の中身を
まるごと貼り付けて **Run**。テーブル・インデックス・RLS・Storage バケットが一度に作られます。
何度実行しても壊れません。

> **すでに稼働中の Supabase がある場合**は、`schema.sql` ではなく
> [マイグレーションの当て方](#マイグレーションの当て方すでに動いている-supabase-がある場合) を見てください。

作られるもの:

| テーブル | 内容 |
|---|---|
| `users` | 参加者（ユーザー名 / ユーザーID / 写真） |
| `match_messages` | 対戦相手とのトーク（試合終了時に削除される） |
| `leagues` | リーグ（主催者・プール構成・状態） |
| `squads` | スカッド（攻撃時/守備時フォーメーション・スタイル・パワー） |
| `entries` | 参加申込（どのプールに入ったか） |
| `matches` | 対戦カードと28項目の試合スタッツ |

### マイグレーションの当て方（すでに動いている Supabase がある場合）

スキーマを変更したときは、`supabase/migrations/` の SQL を番号順に
**SQL Editor** に貼り付けて実行します。どれも何度実行しても安全です。

| ファイル | 内容 |
|---|---|
| `001_user_name_and_user_id.sql` | 名前だけの認証 → ユーザー名 ＋ ユーザーID（合言葉）方式へ |
| `002_league_cancel.sql` | リーグの中止（`cancelled_at` / `cancel_reason` を追加） |
| `003_match_room.sql` | 対戦部屋の番号共有（`room_code` / `room_note` / `room_posted_at` を追加） |
| `004_match_chat.sql` | 対戦相手とのトーク（`match_messages` テーブルを追加） |
| `005_presence_and_proxy.sql` | 在席状況（`users.last_seen_at`）と主催者の代理操作の記録 |
| `006_efl_rank.sql` | EFLランク（`users.rating` / `leagues.category` / `rating_events`） |

**001 を当てると起きること**

1. `users.efootball_id` が `users.user_name` にリネームされます
2. `users.efootball_user_id`（ASLV-569-790-534 形式）が追加されます
3. 既存ユーザーには `TEMP-xxx-xxx-xxx` という仮のIDが自動で入ります
4. `users.display_name` が削除されます

既存ユーザーがいる場合、仮IDのままでは本人が操作できません。
本人から正しいユーザーIDを聞いて、SQL Editor で差し替えてください。

```sql
-- 誰が仮IDのままか確認する
select user_id, user_name, efootball_user_id
  from public.users
 where efootball_user_id like 'TEMP-%';

-- 正しいIDに差し替える
update public.users
   set efootball_user_id = 'ASLV-569-790-534'
 where user_name = 'TOMOYA_10';
```

参加者がまだ少ないうちなら、`users` を空にして登録し直してもらうのが早いです
（`truncate table public.matches, public.entries, public.squads, public.leagues, public.users restart identity cascade;`）。

**002 以降を当てると起きること** — 列とテーブルが増えるだけで、既存データへの影響はありません。

### 3. Storage バケットを確認する

`schema.sql` が `efootleague` という **Public バケット**を作ります。
ダッシュボードの **Storage** に表示されていれば OK です。
（手で作る場合も、名前を `efootleague`、Public bucket を ON にしてください）

### 4. 環境変数を用意する

```bash
cp .env.example .env.local
```

`.env.local` に以下を記入します。

| 変数 | どこで取るか |
|---|---|
| `DATABASE_URL` | Project Settings > **Database** > Connection string > **Connection pooling** の URI。**ポート 6543 / Transaction mode** のものを使い、`[YOUR-PASSWORD]` を実際のパスワードに置き換える |
| `NEXT_PUBLIC_SUPABASE_URL` | Project Settings > API > Project URL |
| `SUPABASE_SERVICE_ROLE_KEY` | Project Settings > API > **service_role** key（**絶対に公開しない**） |
| `SUPABASE_STORAGE_BUCKET` | `efootleague`（変えたなら合わせる） |
| `OPENAI_API_KEY` | OpenAI のダッシュボード。未設定でも手入力でリーグは回せます |
| `OPENAI_MODEL` | 省略可。既定は `gpt-4o-mini` |

> **なぜ 6543 のプーラー URI なのか**
> Vercel はリクエストごとに関数が起動するため、直接接続（5432）だと接続数がすぐ枯渇します。
> Transaction mode ではプリペアドステートメントが使えないので、コード側で `prepare: false` にしてあります。

### 5. 起動する

```bash
npm install
npm run seed -- --reset   # サンプルデータ投入（任意）
npm run dev               # http://localhost:3000
```

### 6. Vercel にデプロイする

1. GitHub にプッシュして、Vercel で **New Project** → リポジトリを選ぶ
2. **Environment Variables** に `.env.local` と同じ 4〜6 個を登録
   （`SUPABASE_SERVICE_ROLE_KEY` と `OPENAI_API_KEY` は Production / Preview のみに）
3. Deploy。ビルド設定は既定のままで動きます

補足:

- Supabase 側で Vercel の IP を許可する設定は不要です（プーラー経由のため）
- 画像は Supabase Storage に入るので、Vercel のファイルシステムには何も書きません
- `npm run export` はローカル（または任意のサーバー）から本番 DB に対して実行します

## EFLランク（レーティング）

リーグ戦の全結果から、参加者の実力を1つの数値で表します。
FIFAランク（2018年改訂版・Eloベース）の式をそのまま使っています。

```
P  = P_before + I × (W − We)
We = 1 / (10^(−dr / 600) + 1)        dr = 自分のレート − 相手のレート
```

| 記号 | 意味 |
|---|---|
| `P_before` | 試合前のレーティング（初期値は全員 **1500**） |
| `W` | 勝ち **1** / 引き分け **0.5** / 負け **0**（PK戦が無いのでこの3通りだけ） |
| `We` | 期待勝率。格上ほど1に近づく |
| `I` | リーグの格。**一般 10 / 賞金あり 25 / 公式 40** |

決めごと:

- 対象は**リーグ戦の承認済みの試合だけ**。決勝トーナメントと中止リーグの試合は含めません
- **得点差は影響しません。** 1-0 も 5-0 も同じ変動です
- 両者の増減は必ず打ち消し合います（誰かが +5 なら相手は −5）
- 反映は**結果が承認された瞬間**です。ホームが登録しただけでは動きません
- 同じ試合が二重に加算されないよう、`rating_events` に `(match_id, user_id)` の一意制約を張っています

### リーグの格

リーグ作成画面で「一般 / 賞金あり / 公式」を選びます。
**公式リーグは運営者だけ**が作れます。`.env.local` と Vercel の環境変数に、
許可するユーザー名をカンマ区切りで設定してください。

```
OFFICIAL_ORGANIZERS=TOMOYA_10
```

未設定なら誰も公式リーグを作れません（一般と賞金ありは誰でも作れます）。

### 過去の試合から初期値を決める

導入時は、これまでの全試合をさかのぼって計算します。やり方は2通りあり、**結果は完全に同じ**です。

**A. Supabase に貼るだけ（手軽）**

`supabase/rating_rebuild.sql` を SQL Editor に貼って実行します。
最後にランキングが表として出ます。ローカル環境は要りません。

**B. 手元から実行（試算できる）**

```bash
npm run rating:rebuild -- --dry   # 計算して結果だけ見る（保存しない）
npm run rating:rebuild            # 実行して保存する
```

`--dry` を付けると保存せずに結果だけ確認できるので、初回はこちらが安心です。

承認された順に1試合ずつたどり、全員 1500 から積み上げ直します。
**何度実行しても同じ結果**になるので、次の場面でも安心して使えます。

- リーグのカテゴリーを後から変えたとき
- 結果を取り消して履歴がずれたと感じたとき

なお、主催者が結果を取り消した場合は、その場で自動的に再計算されます。

### 表示

`/rank` に上位3人の表彰台とランキング表を出します。
リーグの順位表と募集一覧にもレートとカテゴリーのバッジが並びます。
まだ1試合も消化していない人はランキングには載らず、下部に 1500 として表示されます。

| ランク帯 | レート |
|---|---|
| エリート | 1800 以上 |
| プロ | 1650 以上 |
| レギュラー | 1500 以上 |
| チャレンジャー | 1350 以上 |
| ルーキー | 1350 未満 |

## 本人確認のしくみ

**ユーザーIDを入力するのは最初の1回だけです。** 以降はログイン状態が保たれ、
結果登録・承認・部屋番号・トークのどれもIDを聞かれません。48試合こなしても入力は1回です。

しくみ:

- ログイン時に、ユーザーIDを **httpOnly Cookie** に入れます
- 以降のAPIは、リクエストにIDが無ければ Cookie から本人を特定します
- 画面側はユーザーIDを保持しません（JavaScript から読めないので XSS でも盗まれません）
- `SameSite=Lax` なので、他サイトからの POST に Cookie は付きません（CSRF 対策）
- **URLにIDは絶対に載せません。** 履歴・リファラ・スクショから漏れるためです

切り替えは、ヘッダー右上の名前 → 「ログアウト / 別の人に切り替え」から。
各画面の「別の人に切り替える」からも行えます。
以前の版で localStorage に保存していた方は、次にサイトを開いた時点で自動的にログイン状態へ移行します。

---

登録時に2つを入力します。

| 項目 | 例 | 性質 |
|---|---|---|
| **ユーザー名** | `TOMOYA_10` | 公開。リーグ表や対戦カードに表示される。一意 |
| **ユーザーID** | `ASLV-569-790-534` | 秘密。eFootball のマイページに出ているID。一意 |

ユーザーIDは**パスワードの代わり**です。以下の操作はすべてユーザーIDで本人確認します。

- リーグの作成（＝主催者になる）
- 参加申込・スカッド登録
- 試合結果の登録（ホーム側のIDのみ受け付ける）
- 結果の承認・差し戻し（アウェイ側のIDのみ受け付ける）
- リーグの確定（主催者のIDのみ受け付ける）

扱いの決めごと:

- **画面にユーザーIDは一切表示しません。** 「ホーム側の TOMOYA_10 さんだけです」のように、
  権限の説明には常にユーザー名を使います
- 入力欄は既定で伏せ字です（「表示」ボタンで確認できます）
- `GET /api/users` もユーザー名しか返しません。CSV にもユーザーIDは含めません
- 小文字・全角・スペース・区切り無し（`aslv569790534`）で入力しても正規化して受け付けます

## 動作の流れ

**主催側**

1. ユーザー登録（ユーザー名 ＋ ユーザーID ＋写真）
2. リーグ作成（主催者のユーザーID / 1プールの人数 / プール数 / 募集日時）
   - ここで本人確認されたユーザーが主催者になり、この人だけがリーグを確定できます
3. 全試合の承認が終わったら「結果を確定してリーグを終了」

**ユーザー側**

1. ユーザー登録
2. 試合申し込み＋スカッド登録
   （スクショ・スカッド名・**攻撃時/守備時フォーメーション**・チームスタイル・チームパワー）
3. 規定人数（`1プール人数 × プール数`）に達するまでは「準備中」画面
4. 定員到達で **自動締切 → プールへランダム振り分け → 総当たり日程を自動生成**

**リーグ進行（ホーム登録 → アウェイ承認）**

1. プールごとに対戦順（Matchday）が発表される
2. ホームが部屋を立てて番号を貼り、アウェイが確認して対戦する（[対戦部屋の受け渡し](#対戦部屋の受け渡し)）
   - 待ち合わせや回線トラブルの連絡は[トーク](#対戦相手とのトーク)で
3. 試合後、**ホーム側**が結果画面の写真を送信して結果を登録する
4. AI（GPT-4o mini）が画像から 28 項目のスタッツを読み取り、内容を画面で確認
5. 登録スカッド名と画像内のチーム名を自動照合
   - 一致すれば勝敗・得点・失点がそのまま入る
   - 左右が逆なら自動で入れ替え／照合できなければ手動で確認して送信
6. **アウェイ側**が内容を確認して承認、または理由を添えて差し戻す
   - 差し戻すとホームに戻り、理由が表示された状態で登録し直せる
7. 承認された時点でリーグ表と集計に反映（**勝ち点降順 → 得失点差降順 → 総得点降順**）
8. 全試合が承認まで完了すると、主催者が「結果を確定してリーグを終了」を押せる

試合の状態は `scheduled`（未登録）→ `pending`（承認待ち）→ `reported`（承認済み）と遷移します。
承認待ちの結果はリーグ表にも集計にも反映されません。
本人確認はユーザーIDで行い、ホーム以外は登録できず、アウェイ以外は承認できません。

## マイページ（`/me`）

ユーザーIDを入れると、自分の状況がまとめて出ます。一度開けばその端末は記憶するので、
次からは開くだけで表示されます。

- **やること** — 未消化の試合、承認待ち、差し戻し、部屋が立ったかどうかを一覧に。
  自分が動く番のものには印が付き、先頭に並びます
- **申し込んだリーグ** — 参加中のリーグと自分のスカッド、グループ、進捗
- **主催したリーグ** — 自分が立てたリーグと管理画面へのリンク。
  全試合の承認が終わると「結果を確定できます」が出ます

やることの判定は次のとおりです。

| 状況 | ホーム側 | アウェイ側 |
|---|---|---|
| 未消化・部屋なし | 部屋を立てて対戦しましょう | 相手が部屋を立てるのを待ちましょう |
| 未消化・部屋あり | 対戦して結果を登録してください | 番号を確認してください |
| 結果登録済み | 相手の承認待ちです | **承認してください**（要対応） |
| 差し戻された | **登録し直してください**（要対応） | 相手の再登録待ち |

中止・終了したリーグの試合は、やることには出ません。

## 募集が集まらないとき（主催者メニュー）

リーグ画面の「主催者メニュー」から、主催者だけが操作できます。

**今の人数で始める** — 定員に届いていなくても、今いる人数で抽選して開始します。
人数に合わせてグループ数は自動で減り、1グループが2人未満にはなりません
（例: 3人で2グループ希望 → 1グループ3人、9人で4グループ → 3/2/2/2）。
2人未満では開始できません。

**募集人数を変える** — 開始前なら、1グループの人数とグループ数を変更できます。
既に申し込んでいる人数より少ない定員には縮小できません。
変更の結果ちょうど定員に達した場合は、その場で抽選まで進みます。

## フォーメーションの入力

選択式ではなく自由記述です。**数字だけ打てば通ります。**

- スマホでは最初からテンキーが出ます（`type="text"` ＋ `inputMode="numeric"`）
- 全角数字・ハイフン・長音記号（ー）・全角マイナス・スペース・スラッシュは、
  すべて内部で捨てて数字だけを取り出します。`４ー３ー３` も `4 3 3` も `433` と同じ扱いです
- 入力欄から離れた時に `4-3-3` の形へ自動整形します
- 入力中はエラーを出しません。代わりに右端に「7 / 10 人」とだけ出るので、
  打ちながら過不足が分かります。エラーを言うのはフォーカスが外れた時と送信時だけです
- よく使う形はチップでワンタップでも入ります

検証ルール:

| 条件 | メッセージ |
|---|---|
| 3桁か4桁 | 3桁か4桁の数字で入力してください（例: 433 または 4231） |
| 各桁の合計が10 | フィールドプレイヤーの合計が10人になりません（現在◯人） |
| 0を含まない | 0 は使えません。各ラインが1人以上になるように入力してください |

判定は `lib/formation.js` に集約し、**画面とサーバーの両方が同じ関数を使います**。
画面をすり抜けた値も API 側で同じように補正・検証されます。
DBの型は今までどおり text なので、この変更にマイグレーションは不要です。

## 進まない試合をどうにかする

リーグが止まる原因はだいたい「相手が来ない」です。これに2方向から手を打っています。

### 誰が来ていないかが分かる

参加者の名前の横に、最終アクセスからの経過が出ます。

| 表示 | 意味 |
|---|---|
| ● オンライン | 3分以内に操作している |
| ● 5分前 / 2時間前 | 今日は来ている |
| ● 3日前（黄色） | **2日以上来ていない。代理対応を検討する目安** |
| ● 未ログイン | 一度も開いていない |

記録は**既に走っているリクエストのついで**に行うので、常時通信は増えません
（マイページを開く、トークを開く、何か操作する、のいずれかで更新されます）。

マイページの「やること」にも出ます。相手が2日以上来ていない場合は
「◯◯さんは3日前から来ていません。主催者に相談すると代理で処理してもらえます」と表示されます。

### 主催者が代理で終わらせられる

試合ページの下部に「相手が反応しない場合はこちら」があります。主催者のユーザーIDでのみ操作できます。

- **代理で承認** — ホームが登録済みで、アウェイが承認できない場合
- **不戦勝として処理** — 3-0 / 0-3 / 両者不参加の 0-0 をワンタップで。スクリーンショットは不要です
- **スコアを指定して確定** — 対戦は済んだのに登録されない場合に、聞き取った点数で確定
- **結果を取り消す** — 誤って確定したときに未消化へ戻す

**代理操作は必ず記録され、試合ページに「〇〇さん（主催者）が代理で処理しました」と理由つきで表示されます。**
主催者が当事者の試合も操作できてしまう以上、隠さないことでバランスを取る方針です。
メモ欄に経緯（「3日連絡つかず、本人合意のうえ」など）を残せます。

## 対戦部屋の受け渡し

参加者同士が直接連絡を取れなくても対戦できるように、部屋番号をサイト経由で渡します。
試合ページ（`/matches/[id]/report`）の上部にパネルがあります。

1. **ホーム**が eFootball で部屋を立て、パネルに部屋番号を貼る（ひとこと欄にパスワードや待ち時間も書けます）
2. **アウェイ**が自分のユーザーIDを入れて「確認する」を押すと、番号が表示される
3. 試合が終わってアウェイが結果を承認すると、番号は**自動で消えます**

決めごと:

- 貼れるのはホームだけ。見られるのはその試合の**対戦2人だけ**です
- 番号はページのHTMLに**一切埋め込みません**。「確認する」を押したときだけ取りに行きます
  （URLに残らないよう、確認も POST で行っています）
- リーグ表の対戦カードには「部屋あり」バッジだけが出ます。番号は出ません
- ホームは番号の貼り直し・取り消しができます

## 対戦相手とのトーク

「部屋立てた？」「回線落ちた」といった状況共有ができるよう、試合ごとのテキストチャットがあります。
対戦部屋パネルのすぐ下に出ます。

- 使えるのは**その試合の2人だけ**。ユーザーIDを入れて開きます
- 開いている間は**5秒ごとに新着を取りに行きます**（差分だけ。タブが裏なら休みます）
- 「部屋立てました」「回線が落ちました」などの定型文をタップで送れます
- 1通300文字まで
- **試合結果が承認されると、やり取りはDBから削除されます。** トークは試合中の連絡用と割り切っています
- 中止・確定済みのリーグでも見られません

秘匿の扱いは部屋番号と同じで、本文はページのHTMLに埋め込まず、開いたときだけ取りに行きます
（ユーザーIDがURLに残らないよう、読み取りも POST です）。

## 取り消しと中止

**参加取り消し（参加者）** — 準備中の画面から「参加を取り消す」。

- 組み合わせ抽選の**前だけ**。抽選後は日程が崩れるので取り消せません
- 本人のユーザーIDでのみ実行できます
- 登録したスカッドも一緒に削除されます（他から参照されていない場合のみ）
- 取り消した後、同じリーグに申し込み直せます

**リーグの中止（主催者）** — リーグ画面の「このリーグを中止する（主催者）」。

- 主催者のユーザーIDでのみ実行できます。理由を添えられます
- 中止すると **募集一覧から消えます**。申し込み・結果の登録・承認・確定もすべて拒否されます
- 直リンクでは開けて、「中止されました」と理由が表示されます
- 公開集計（`/data`）の対象からも外れます。中途半端なリーグの結果が勝率表を荒らしません
- **記録は消えません。**「再開」すれば元の状態（募集中／開催中）にそのまま戻ります
- 確定済みのリーグは中止できません

内部的には `status` を書き換えず、`cancelled_at` が入っているかどうかで中止中を表しています。
だから再開が安全にできます。

> **運営向け CSV には中止したリーグの試合も含まれます。**
> 公開集計から外すのは「みんなが見て楽しいデータ」を守るためで、
> 分析用の生データは欠けさせない、という切り分けです。
> 除外したい場合は `league_id` で絞ってください
> （中止中のリーグは `select league_id from leagues where cancelled_at is not null` で分かります）。

完全に削除したい場合は SQL Editor から行ごと消します（`matches` と `entries` は連動して消えます）。

```sql
delete from public.leagues where league_id = 12;
```

## 決勝トーナメント表

グループリーグの下に、W杯と同じ形式のトーナメント表を表示します。

- 各グループの**上位2名**が進出。「A組1位 × B組2位」のたすき掛けで組みます
- そのグループの全試合が承認されると、枠にチーム名が入ります（未確定の組は「未確定」表示）
- プール数が奇数のときは余ったグループの1位×2位、2の冪でないときは不戦勝で埋めます
- 現状は**表示のみ**。トーナメントの対戦・結果登録は今後のアップデートで対応します

## データの扱い（公開 / 運営）

**公開しているもの（`/data`）** — みんなが見て楽しめる集計だけ。試合が承認されるたびに更新されます。

- 歴代の大会結果（大会名・参加人数・各グループの優勝者）
- フォーメーション別の勝率（試合数・勝分敗・平均得失点・平均勝点）
- フォーメーション相性表（縦＝自分 / 横＝相手、セルは勝率と試合数）

トーナメントが未実装なので、優勝者は**グループ1位**（勝点→得失点差→総得点）としています。
複数グループの大会では、各グループの優勝者を並べて表示します。
終了した大会は募集一覧には出ず、結果はここでだけ見られます。

**公開していないもの** — 個々の試合スタッツ、スカッド一覧、参加者マスタ、CSV。
サイト上にダウンロード口は一切ありません（CSV 配布用の API ルートは存在しません）。
DB 側も全テーブルで RLS を有効にし、ポリシーを作っていないため、
anon キーが漏れても外部からは1行も読めません。読み書きはサーバー側の接続だけです。

**運営による取り出し** — 手元で CLI から実行します（`.env.local` の `DATABASE_URL` を見ます）。

```bash
npm run export                          # exports/ に3ファイル出力
npm run export -- --out /path/to/dir    # 出力先を指定
npm run export -- --stdout matches.csv  # 標準出力へ（パイプ処理用）
```

出力される CSV:

- `matches.csv` — `match_id, league_id, home_squad_id, away_squad_id, home_team_name, away_team_name, match_result, home_score … away_saves`（全35列 / 承認済みの試合のみ）
- `squads.csv` — `squad_id, user_id, team_name, attack_formation, defence_formation, team_style, team_power`
- `user.csv` — `user_id, user_name`（ユーザーIDは合言葉なので出力しません）

`league_id` / `home_squad_id` / `away_squad_id` を含めているので、`squads.csv` と結合すれば
「どの攻撃時/守備時フォーメーション・チームパワー・チームスタイルで戦った試合か」を辿れます。

## 止まらないための作り

サーバーレスでは、1つの関数が長く居座ると他の処理まで巻き添えになります。
そうならないよう、次の歯止めを入れてあります。

**時間の上限をすべてに明示** — 関数が長時間占有されることを構造的に防ぎます。

| 対象 | 上限 |
|---|---|
| AI画像解析 | 60秒 |
| その他のAPI | 15秒 |
| DBを見るページ | 20秒 |
| OpenAI呼び出し | 40秒（再試行1回まで） |
| DBクエリ | 15秒 |

上限を超えたら、その1リクエストがエラーになるだけで、サーバー全体は生きています。
AIが時間切れになった場合は「手入力で登録してください」に落ちます。

**画像はブラウザ側で縮めてから送る** — `lib/image.js`

- 試合結果は長辺1920px / JPEG画質85（AIが数字を読むので解像度は残す）
- スカッド画像は1600px、プロフィール写真は640px
- 十分小さい画像はそのまま送る。失敗しても元の画像で送信は続行する
- 実測でスクショは半分以下になります。Vercelのボディ上限4.5MBに対して余裕ができます
- サーバー側でも4MB超は明示的に断ります

**通信の回数を減らす** — トークは1回のポーリングでDBを**1往復**だけにしました
（以前は4往復）。間隔も10秒に延ばし、タブが裏なら休み、15分動きが無ければ自動で止まります。

## 困ったときは

```bash
npm run doctor
```

Next.js を通さずに DB へ直接つないで、名前解決・接続・各クエリの所要時間・同時実行の可否を
順に測ります。「画面が開かない」ときに、原因が **DB 側か Next.js 側か**を切り分けられます。

よくある詰まり方:

| 症状 | 原因 | 対処 |
|---|---|---|
| 接続に数秒以上かかる | Supabase プロジェクトが一時停止 | ダッシュボードで再開する |
| `N本同時` で止まる | 接続プールが詰まっている | `.env.local` に `PGPOOL_MAX=1` |
| DB は速いのに画面が重い | `next dev` の初回コンパイル | `rm -rf .next && npm run dev` |
| 関数が300秒でタイムアウト | 上限未設定のルートが残っている | `maxDuration` が入っているか確認 |
| DBのRTTが100ms超 | Vercelのリージョンが遠い | Vercelのリージョンを東京（`hnd1`）に |

なお、ページ内で複数のクエリを投げる場合も**並列にせず1本ずつ**流しています。
どれも数十msなので並列にする利点がなく、プーラー経由だと同時実行で詰まることがあるためです。
クエリには15秒のタイムアウトを入れてあるので、無言で固まらずエラーとして表に出ます。

## 検証済みの動作

実際の PostgreSQL 18 に `schema.sql` を適用し、そこに接続して確認しています。

- スキーマ適用（5テーブル / matches 45カラム / 全テーブル RLS 有効）
- **マイグレーション 001**: 移行前スキーマを再現してから適用し、
  リネーム・仮ID付与・制約追加が通ること、2回続けて実行しても壊れないこと、
  不正な形式のIDが DB の CHECK 制約で弾かれること
- **本人確認**:
  - 登録時のバリデーション（形式不正 / ユーザー名の重複 / ユーザーIDの重複 /
    同一人物の再登録はログイン扱い）
  - 小文字・スペース入り・区切り無しのIDを正規化して受け付けること
  - 結果登録をアウェイのID・第三者のID・ID未入力で試して全て拒否されること
  - 承認をホーム自身のIDで試して拒否されること
  - 確定を参加者（非主催者）のIDで試して拒否されること
  - `GET /api/users` とレンダリング後のHTMLにユーザーIDが1件も含まれないこと
- seed 投入と、総当たり日程の生成・勝ち点／得失点差による並び替え
- 数値型が文字列で返らないこと（`played` / `avg_gf` / `team_power` などが number）
- スカッド名の自動照合（正順・左右逆・不一致）
- 承認フロー一連（ホーム登録 → 差し戻し（理由が画面に表示される）→ 再登録 → 承認 → 確定）
- 相性表の整合性（視点展開行数＝試合数×2、勝分敗の合計、勝率の範囲、行列の対称性）
- **EFLランク**: 計算式が要望書どおりか（We の値、ゼロサム、得点差が影響しないこと、
  格差がある対戦での増減の非対称性、I による倍率）、承認した瞬間だけ反映されること、
  二重加算されないこと、取り消しで巻き戻ること、再計算が何度実行しても同じ値になること、
  公式リーグを運営者以外が作れないこと
- **ログイン**: 形式不正・未登録IDの拒否、ログイン後に**IDを一切送らずに**
  マイページ・トーク・部屋番号・結果登録ができること、
  Cookie が `HttpOnly` `SameSite=lax` `Secure` で発行されること、
  別人に切り替えると権限が正しく変わること（アウェイは結果登録できず承認はできる）、
  ログアウト後は操作できなくなること、明示指定は引き続き通ること、
  ログイン後の画面からID入力欄が消えること
- **在席状況**: マイページを開く／トークを開く操作で `last_seen_at` が更新されること、
  リーグ画面と試合ページに表示されること
- **主催者の代理操作**: 非主催者の拒否、不戦勝での確定（3-0 が `home_win` として記録され
  `match_source = organizer` になること）、代理承認、結果の取り消しで未消化に戻ること、
  代理の事実と理由が試合ページに表示されること
- **フォーメーション入力**: 27パターンの入力を網羅テスト（全角数字・長音記号・全角マイナス・
  U+2010ハイフン・全角/半角スペース・スラッシュ・英字混入・前後空白・null/undefined・
  2桁/5桁・合計9/11・0混入）。既存の候補16件がすべて有効なことも確認
- **主催者メニュー**: 非主催者の操作拒否、二重開始の拒否、1人での開始拒否、
  申込人数より小さい定員への縮小拒否、定員ちょうどへの縮小でその場抽選、
  人数分配（8→[4,4] / 7→[4,3] / 3人2グループ希望→[3] / 9人4グループ→[3,2,2,2]、
  合計一致と各グループ2人以上）
- **マイページ**: 未登録ID・ID未入力の拒否、レスポンスに他人のユーザーIDが含まれないこと、
  試合の進行に応じてやることが変化すること（部屋なし→部屋あり→承認待ち→差し戻し→完了で消える）を
  ホーム・アウェイ両視点で確認
- **募集一覧**: 終了した大会が出ないこと。**データ画面**: 大会名と各グループ優勝者が出ること
- **トーク**: 第三者・未登録ID・ID未入力での閲覧拒否、空文字と301文字の投稿拒否、
  差分取得（`after_id`）、自分/相手の判定、HTMLに本文が含まれないこと、
  承認と同時に閲覧不可になりDBからも消えること（0件を確認）
- **対戦部屋**: アウェイや第三者・未登録IDでは貼れない/見られないこと、番号が空なら弾かれること、
  対戦2人だけが確認できること、リーグ表と試合ページのHTMLに番号が含まれないこと、
  承認と同時に自動で消えること、承認後は貼り直せないこと
- **参加取り消し**: 未登録ID / 申し込んでいない人 での取り消しが拒否されること、
  本人なら成功して孤立スカッドも消えること、取り消し後に申し込み直せること、
  抽選後（開催中）は拒否されること
- **リーグ中止**: 非主催者の中止拒否 / 二重中止の拒否 / 募集一覧とAPI一覧から消えること /
  直リンクでは理由つきで見られること / 中止中は申し込み・結果登録（ホーム本人でも）・確定が
  すべて拒否されること / 公開集計から除外されること / 再開すると元の状態と集計値に戻ること
- `/api/export/*` が 404 であること、`npm run export` の3ファイル出力と `--stdout`
- Storage クライアントの初期化と公開URLの組み立て
- `next build` の成功と全ページの 200 応答

未検証: 実際の Supabase インスタンスへの接続と、Storage への実アップロード
（サンドボックスから外部通信ができないため）。手順どおりに環境変数を入れれば動く想定です。

## 現状の割り切り

- ユーザーIDを知っている人はその人になりすませます（パスワードと同じ性質）。
  IDは平文で保存しているので、DB が漏れれば全員のIDが漏れます。
  本格的に守るなら、ハッシュ化やセッション方式への移行を検討してください。
- ログイン状態という概念はなく、操作のたびにIDを入力します
  （同じ端末なら localStorage から自動入力されます）。
- 承認の督促・通知機能はありません。承認待ちはリーグ表のバッジとマイページで確認します。
- 主催者は自分が当事者の試合も代理で確定できます（そうしないと主催者の試合が詰むため）。
  代わりに、代理操作の事実と実行者を必ず画面に表示しています。
- 募集終了日時（`recruit_start` / `recruit_end`）は表示だけで、締切は自動化されていません。
  集まらないときは主催者メニューから手動で始めるか、中止します。
- トークはポーリング（5秒間隔）で、リアルタイム配信ではありません。
  通知も無いので、相手がページを開いていなければ気づかれません。
- 中止したリーグは主催者以外からは一覧に出ないだけで、URL を知っていれば誰でも見られます。
- 開催中のリーグを中止しても、既に承認された試合の記録はそのまま残ります
  （公開集計からは外れますが、再開すれば戻ります）。
- トーナメントは表示のみで、対戦・結果登録には未対応です。
- Storage バケットは Public です（画像URLを知っていれば誰でも見られます）。
